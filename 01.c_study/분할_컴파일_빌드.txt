1. 분할 컴파일이란

프로그램을 여러 .c 파일로 나누고, 파일마다 따로 컴파일한 뒤 하나로 묶는 방법이다.

  main.c --(컴파일 cl -c)--> main.obj --+
                                        +--(링크 link)--> main.exe
  calc.c --(컴파일 cl -c)--> calc.obj --+
          (calc.h는 두 .c 파일이 #include 한다)

- 컴파일: .c 파일 하나가 .obj 파일(기계어 조각) 하나가 된다. 이때 컴파일러는 그 .c 파일
  하나만 본다. 다른 파일에 있는 함수는 헤더(.h)에 적힌 선언(원형)으로만 안다.
- 링크: 링커가 .obj 파일들과 C 라이브러리를 모아 .exe 하나를 만든다. 선언만 보고 부른
  함수가 실제로 어느 .obj에 있는지 여기서 찾아 연결한다.
- 그래서 오류도 두 가지이다.
    컴파일 오류  error C2143 등 C로 시작. "파일(줄): error ..." 형태라 F9로 그 줄에 간다.
    링크 오류    error LNK2019 등 LNK로 시작. 줄 번호가 없다. 파일을 빠뜨렸거나(함수를
                 못 찾음) 같은 것을 두 번 정의했을 때 난다(9절).
- 좋은 점: 코드가 기능별로 정리되고, 큰 프로그램에서는 고친 파일만 다시 컴파일하면 된다.


2. 이 폴더에서 쓸 수 있는 방법 세 가지

이 폴더의 build.bat(gvim Alt+m, Emacs M-m, F5가 쓰는 것)는 "현재 프로그램" 파일 하나만
빌드한다. main.c만 빌드되고 calc.c는 빠지므로, 그대로 쓰면 링크 오류 LNK2019가 난다.
여러 파일을 빌드하는 방법은 다음 세 가지이다.

  1. 프로젝트 폴더에 build.bat 두기 (4절, 권장)
     편집기: gvim Alt+m, F9 / Emacs M-x make-without-asking
     특징: 그 폴더의 .c를 모두 컴파일해서 링크한다. 가장 편하다.
  2. 명령줄에서 cl, link로 직접 (5절)
     편집기: 쓰지 않는다
     특징: 분할 컴파일의 순서(컴파일 → 링크)를 그대로 본다. 고친 파일만 다시 컴파일할 수 있다.
  3. #include "calc.c" (6절)
     편집기: 지금 그대로 (Alt+m, M-m, F5)
     특징: 실제로는 한 파일로 컴파일한다(분할 컴파일이 아니다). 짧은 연습용.

더 큰 프로젝트(여러 폴더, C와 C++ 섞기)는 따로 만든 작업 공간 E:\Work\Dev\03.c_project가
있다(new_project.bat로 프로젝트를 만들고 build.bat 프로젝트이름으로 빌드한다. 그 폴더의
C_C++_프로젝트_가이드.md 참고).


3. 예제 프로젝트 c\calc (main.c, calc.h, calc.c)

프로그램 하나 = 폴더 하나로 만든다. 다른 예제와 섞이지 않게 c 폴더 아래에 새 폴더를 둔다.

  E:\Work\Dev\01.c_study\
      build.bat, shell.bat, run.bat, Turboc.h    이 폴더의 파일 (그대로 둔다)
      c\
          calc\                프로젝트 폴더
              main.c           main 함수
              calc.h           calc.c에 있는 함수와 변수의 선언
              calc.c           함수와 변수의 정의
              build.bat        방법 1에서 만든다 (4절)
              build\           빌드 결과 (자동으로 생긴다)

폴더와 파일 만들기

- 폴더를 먼저 만든다. 없는 폴더에 파일을 저장하면 gvim은 "E212: 쓸 파일을 열 수 없습니다"를
  낸다.
    PowerShell:   mkdir E:\Work\Dev\01.c_study\c\calc
    gvim:         :call mkdir('c\calc', 'p')   (Alt+x를 누르고 call mkdir('c\calc', 'p') Enter)
- gvim: Alt+f c\calc\main.c Enter, Alt+f c\calc\calc.h Enter, Alt+f c\calc\calc.c Enter
  (Alt+f의 이름은 공부 폴더 기준이다). Emacs: M-f c/calc/main.c C-j.
- 새 .c 파일에는 main 틀이, 새 .h 파일(gvim)에는 include guard가 자동으로 들어간다.
  calc.c에는 main이 있으면 안 되므로 틀을 지우고 쓴다(gvim: Esc 뒤 ggdG, Emacs: C-x h C-w).
  main이 두 개면 LNK2005가 난다.

calc.h (선언만 둔다)

  #if !defined(CALC_H)

  // calc.c에 있는 함수와 변수의 선언. 이 함수들을 쓰는 .c 파일은 이 헤더를 포함한다.
  int Add(int A, int B);
  int Multiply(int A, int B);
  double Average(const int *Values, int Count);

  // 변수는 extern으로 선언만 한다. 정의(메모리를 잡는 곳)는 calc.c에 한 번만 있다.
  extern int CallCount;

  #define CALC_H
  #endif

  include guard(#if !defined ... #endif)는 한 .c 파일에서 이 헤더가 두 번 포함되어도 한
  번만 읽히게 한다. gvim이 새 .h에 넣어 주는 형식이며, 교재의 #ifndef CALC_H / #define
  CALC_H / ... / #endif와 같은 뜻이다.

calc.c (정의를 둔다)

  #include "calc.h"

  // 전역 변수의 정의. 프로그램 전체에서 한 파일에만 있어야 한다.
  int CallCount = 0;

  // static 함수는 이 파일 안에서만 보인다. 다른 파일에 같은 이름이 있어도 된다.
  static void
  CountCall(void)
  {
      ++CallCount;
  }

  int
  Add(int A, int B)
  {
      CountCall();
      return(A + B);
  }

  int
  Multiply(int A, int B)
  {
      CountCall();
      return(A * B);
  }

  double
  Average(const int *Values, int Count)
  {
      int Total = 0;
      for(int Index = 0; Index < Count; ++Index)
      {
          Total += Values[Index];
      }
      CountCall();
      return((double)Total / Count);
  }

main.c

  #include <stdio.h>
  #include "calc.h"

  int
  main(void)
  {
      int Scores[] = {90, 85, 77};

      printf("3 + 4 = %d\n", Add(3, 4));
      printf("3 * 4 = %d\n", Multiply(3, 4));
      printf("평균 = %.2f\n", Average(Scores, 3));
      printf("calc.c의 함수를 %d번 불렀다\n", CallCount);
      return(0);
  }

실행 결과

  3 + 4 = 7
  3 * 4 = 12
  평균 = 84.00
  calc.c의 함수를 3번 불렀다

- #include <...>는 컴파일러의 표준 헤더, #include "..."는 내 헤더이다. "..."는 그 .c 파일과
  같은 폴더에서 먼저 찾는다.
- 함수 이름을 반환형 다음 줄 맨 앞에 쓰는 형식(int / Add(...))이라야 gvim Alt+j의 함수
  목록에 나온다.


4. 방법 1: 프로젝트 폴더에 build.bat 두기 (권장)

gvim의 Alt+m은 지금 파일이 있는 폴더부터 위로 올라가며 가장 가까운 build.bat를 실행한다.
Emacs의 M-x make-without-asking(Casey의 빌드 명령)도 같다. 그래서 프로젝트 폴더에 그 폴더의
.c 파일을 모두 빌드하는 build.bat를 두면, 프로젝트 안의 어느 파일에서든 프로그램 전체가
빌드된다.

4.1 build.bat 만들기

c\calc\build.bat로 아래 내용을 저장한다(gvim: Alt+f c\calc\build.bat Enter, 붙여넣기,
Alt+s). 한글 없이 영문만 쓴다(배치 파일은 영문과 CRLF 줄 끝이 안전하다. gvim이 Windows
줄 끝으로 저장한다).

  @echo off
  setlocal

  rem Builds every .c file in this folder into one program, build\main.exe.
  rem Put this file in a project folder inside the C/C++ study folder.
  rem   build.bat            from cmd or PowerShell in this folder
  rem   Alt+m in gvim        gvim runs the nearest build.bat above the file
  rem   M-x make-without-asking in Emacs   the same
  rem name= is the .c file that has main(): gvim's F5 and Emacs's F5 run
  rem build\<that name>.exe while that file is the current program.
  set "name=main"

  rem The study folder is the nearest folder above this one with shell.bat.
  set "study=%~dp0"
  :find_study
  if exist "%study%shell.bat" goto found_study
  for %%D in ("%study%.") do set "parent=%%~dpD"
  if /i "%parent%"=="%study%" (
      >&2 echo shell.bat of the C/C++ study folder was not found above "%~dp0".
      exit /b 1
  )
  set "study=%parent%"
  goto find_study
  :found_study

  call "%study%shell.bat"
  if errorlevel 1 exit /b %errorlevel%

  rem The flags of the study folder's build.bat (C17, debug build).
  set CommonCompilerFlags=-nologo -FC -Z7 -Od -MTd -RTC1 -W4 -source-charset:utf-8 -D_CRT_SECURE_NO_WARNINGS -D_CRT_NONSTDC_NO_WARNINGS -std:c17
  set CommonLinkerFlags=-incremental:no user32.lib gdi32.lib

  if not exist "%~dp0build\" mkdir "%~dp0build"
  pushd "%~dp0build" || exit /b 1

  rem A running program locks its exe, and the link would fail with LNK1168.
  if not exist "%name%.exe" goto compile
  2>nul (>>"%name%.exe" call ) && goto compile
  >&2 echo %name%.exe is running. Close it ^(Shift+F5 in gvim^) and build again.
  popd
  exit /b 1

  :compile
  rem cl compiles each .c file into its own .obj here in build\, then links them.
  cl %CommonCompilerFlags% -I"%study%." "%~dp0*.c" -Fe"%name%.exe" /link %CommonLinkerFlags%
  set "status=%errorlevel%"
  popd
  if "%status%"=="0" echo Built %~dp0build\%name%.exe
  exit /b %status%

하는 일
- 위쪽 폴더에서 shell.bat를 찾아 Visual Studio 2022 컴파일러를 준비한다(c\calc, c\a\b처럼
  공부 폴더 안 어디에 두어도 된다).
- 이 폴더의 *.c를 모두 컴파일해서 build\main.obj, build\calc.obj를 만들고 build\main.exe로
  링크한다. 옵션은 이 폴더의 build.bat와 같다(C17, 디버그 빌드, 경고 수준 4, UTF-8 소스).
- 공부 폴더를 포함 경로(-I)에 넣으므로 #include "Turboc.h"도 된다(8절).
- 프로그램이 실행 중이면 빌드하지 않고 알려 준다.
- 매번 모든 .c를 컴파일한다. 연습 프로그램은 금방 끝난다. 고친 파일만 컴파일하는 순서는
  5절에 있다.
- 다른 프로젝트에서는 이 파일을 복사해서 쓴다. main이 있는 파일 이름이 main.c가 아니면
  set "name=main"의 main을 그 이름(확장자 빼고)으로 바꾼다.

4.3 gvim

- Alt+m: main.c, calc.c, calc.h 어느 파일에서 눌러도 c\calc\build.bat가 실행되어 프로그램
  전체가 빌드된다(빌드 창 제목이 "build: ...\c\calc\build.bat"). 고친 파일은 빌드 전에 모두
  저장된다.
- F9, Alt+n, Alt+Shift+n: 오류가 calc.c에 있으면 calc.c의 그 줄로 간다.
- F5, Ctrl+F5, Shift+F5, F6는 "현재 프로그램"(상태 줄의 [이름])의 build\이름.exe를 쓴다.
  [main.c]일 때 build\main.exe가 실행된다.
  calc.c를 고치러 들어가면 현재 프로그램이 [calc.c]로 바뀌고, F5는 "Nothing to run. Build
  calc.c first (Alt+m)."를 낸다. Ctrl+^(바로 전 파일) 또는 Alt+b main.c Enter로 main.c에
  돌아온 뒤 F5(또는 Ctrl+F5)를 누른다. Alt+m은 어느 파일에서나 된다.

  순서 예: calc.c 고치기 → Alt+m (build ok) → Ctrl+^ (main.c로) → F5

4.4 Emacs

- M-m은 이 폴더의 build.bat로 현재 파일 하나만 빌드하므로 프로젝트에서는 LNK2019가 난다.
  대신 M-x make-without-asking Enter를 쓴다. 지금 파일 위쪽에서 가장 가까운 build.bat

  (M-x 다음 make-w Tab으로 이름을 완성할 수 있다. 다시 빌드는 M-x recompile.)
- F5는 현재 프로그램(모드 줄의 [이름])의 build\이름.exe를 실행한다. main.c를 보고 있을 때
  F5를 누른다. C-F5는 M-m과 같은 한 파일 빌드를 하므로 프로젝트에서는 쓰지 않는다.


5. 방법 2: 명령줄에서 cl과 link로 직접

분할 컴파일의 순서(컴파일 → 링크)를 그대로 해 보는 방법이다.

5.1 컴파일러 창 열기

cl과 link는 Visual Studio의 환경이 준비된 창에서만 실행된다.
- PowerShell에서:   cmd /k E:\Work\Dev\01.c_study\shell.bat
  (PowerShell에서 shell.bat를 바로 실행하면 환경이 남지 않는다. cmd /k로 연 cmd 창에서
  아래 명령을 친다.)
- 또는 시작 메뉴의 "x64 Native Tools Command Prompt for VS 2022".

  cd /d E:\Work\Dev\01.c_study\c\calc
  if not exist build mkdir build
  set F=-nologo -FC -Z7 -Od -MTd -RTC1 -W4 -source-charset:utf-8 -D_CRT_SECURE_NO_WARNINGS -D_CRT_NONSTDC_NO_WARNINGS -std:c17

  F는 이 폴더 build.bat의 옵션이다. 꼭 필요한 것은 -source-charset:utf-8(gvim이 UTF-8로
  저장한 소스의 한글을 바르게 읽는다)이고, -Z7은 디버깅 정보, -W4는 경고, -std:c17은 C 표준
  이다.

5.2 한 번에: cl이 컴파일과 링크를 모두 한다

  cl %F% main.c calc.c -Febuild\main.exe -Fobuild\
  build\main.exe

  -Fe는 만들 exe, -Fo는 .obj를 둘 폴더(끝에 \를 붙인다)이다. 결과: build\main.obj,
  build\calc.obj, build\main.exe, build\main.pdb(디버깅 정보). 파일 이름 대신 *.c라고 써도
  된다(cl %F% *.c -Febuild\main.exe -Fobuild\).

5.3 두 단계로: 컴파일(-c)과 링크를 따로

  cl %F% -c main.c calc.c -Fobuild\
  link -nologo -debug build\main.obj build\calc.obj -out:build\main.exe
  build\main.exe

  -c는 "컴파일만 하고 링크하지 않는다"이다. link의 -debug는 디버깅 정보(.pdb)를 만든다.

5.4 고친 파일만 다시 컴파일

calc.c만 고쳤으면 calc.c만 다시 컴파일하고 링크한다. main.obj는 그대로 쓴다.

  cl %F% -c calc.c -Fobuild\
  link -nologo -debug build\main.obj build\calc.obj -out:build\main.exe

  calc.h(헤더)를 고쳤으면 그 헤더를 #include 하는 .c를 모두 다시 컴파일한다. 헷갈리면
  5.2처럼 전부 다시 빌드한다.

5.5 Turboc.h나 공부 폴더의 헤더를 쓸 때

  cl %F% -I..\.. main.c calc.c -Febuild\main.exe -Fobuild\

  -I는 헤더를 찾을 폴더를 더한다. ..\..은 c\calc에서 본 공부 폴더이다.


6. 방법 3: #include "calc.c"로 한 파일처럼 빌드

main.c가 calc.c를 #include 하면, 컴파일러에는 두 파일이 한 파일로 보인다. 이 폴더의
build.bat, gvim Alt+m, Emacs M-m, F5를 그대로 쓸 수 있다.

  // main.c
  #include <stdio.h>
  #include "calc.h"
  #include "calc.c"    // calc.c의 내용이 여기에 들어온다

- 빌드: main.c를 연 상태에서 Alt+m(Emacs M-m), 실행 F5. 명령줄에서는
  .\build.bat c\calc\main.c
- 방법 1의 build.bat가 없는 폴더에서 쓴다. 그 폴더에 build.bat가 있으면 gvim Alt+m이 그것을
  실행해서 calc.c를 두 번 컴파일하게 된다(LNK2005).
- calc.c를 따로 빌드하거나 방법 1, 2와 함께 쓰면 안 된다. 함수가 두 번 들어가서
  LNK2005 "...이(가) main.obj에 이미 정의되어 있습니다", LNK1169가 난다.
- calc.c를 연 채(현재 프로그램 [calc.c]) Alt+m을 누르면 calc.c만 빌드되어 main이 없으므로
  LNK1561 "진입점이 정의되어야 합니다"가 난다. main.c로 돌아가서 빌드한다.
- 실제로는 파일 하나로 컴파일하는 것이라(unity build) 분할 컴파일은 아니다. 두 .c 파일에
  같은 이름의 static 함수가 있으면 충돌한다. 짧은 연습용으로 쓴다.


7. 파일을 나눌 때의 규칙

- 헤더(.h)에는 선언만 둔다: 함수 원형, 구조체와 typedef, #define 상수, extern 변수 선언.
- .c에는 정의를 둔다: 함수 본문, 전역 변수(int CallCount = 0;).
- 같은 함수나 전역 변수의 정의는 프로그램 전체에 한 번만 있어야 한다. 헤더에
  int CallCount = 0;처럼 정의를 쓰면 그 헤더를 포함한 .c마다 정의가 생겨 LNK2005가 난다.
  헤더에는 extern int CallCount;, 정의는 .c 한 곳.
- 함수를 쓰는 .c 파일은 그 함수가 선언된 헤더를 반드시 #include 한다. 빠뜨리면 C에서는
  오류가 아니라 경고 C4013만 나고 빌드는 된다. 하지만 반환형을 int로 짐작하므로 double을
  돌려주는 Average가 엉뚱한 값(평균 = 0.00)을 낸다. C4013 경고는 오류처럼 고친다.
- 각 .c는 자기 헤더도 #include 한다(calc.c가 calc.h를). 선언과 정의가 다르면 컴파일러가
  알려 준다.
- 한 파일 안에서만 쓰는 함수와 전역 변수는 static을 붙인다(calc.c의 CountCall). 다른
  파일의 같은 이름과 부딪히지 않는다.
- 모든 헤더에 include guard를 둔다.
- main 함수는 프로그램 전체에 하나뿐이다.


8. Turboc.h를 여러 파일에서 쓸 때

이 폴더의 Turboc.h는 clrscr, gotoxy 같은 함수의 본문까지 헤더 안에 들어 있다(교재의 원래
형식). 그래서 한 프로그램의 두 .c 파일이 그대로 #include "Turboc.h" 하면 함수가 두 번
정의되어 LNK2005("clrscr이(가) main.obj에 이미 정의되어 있습니다" 등)가 난다.

한 파일만 그대로 포함하고, 나머지 파일에서는 포함하기 전에 TURBOC_PROTOTYPE_ONLY를 정의한다.
그러면 그 파일에는 선언만 들어간다.

  // main.c (함수 본문은 여기 한 곳에만)
  #include "Turboc.h"

  // screen.c (다른 파일)
  #define TURBOC_PROTOTYPE_ONLY
  #include "Turboc.h"

delay, randomize, random은 매크로라서 어느 파일에서나 그대로 쓸 수 있다.


9. 자주 나는 오류와 해결

  LNK2019, LNK2001 "확인할 수 없는 외부 기호" + LNK1120
      선언(헤더)은 있는데 정의가 빌드에 들어오지 않았다.
      - 파일 하나만 빌드했다: 이 폴더의 build.bat, gvim의 프로젝트 build.bat 없는 Alt+m,
        Emacs M-m, cl main.c만, link에 calc.obj를 빼먹음.
        → 방법 1의 build.bat 또는 cl main.c calc.c로 모두 빌드한다.
      - 함수 이름 철자가 선언과 정의에서 다르다.
  LNK2005 "...이(가) ...obj에 이미 정의되어 있습니다" + LNK1169
      같은 것이 두 번 정의되었다.
      - 헤더에 변수 정의(int X = 0;)나 함수 본문을 썼다 → 헤더에는 선언만(7절).
      - #include "calc.c"를 쓰면서 calc.c도 따로 빌드했다(6절).
      - Turboc.h를 두 파일에서 그대로 포함했다(8절).
      - main이 두 개다(새 .c 파일에 들어간 main 틀을 지우지 않았다).
  LNK1561 "진입점이 정의되어야 합니다"
      main이 없는 파일 하나만 빌드했다(현재 프로그램이 calc.c인 채 Alt+m 등).
      → main.c로 돌아가서 빌드하거나 방법 1을 쓴다.
  LNK1168 exe를 열 수 없다 / "main.exe is running"
      프로그램이 실행 중이거나 디버깅 중이다. 실행 창에서 키를 누르거나 Shift+F5.
  warning C4013 "'Add'이(가) 정의되지 않았습니다. extern은 int형을 반환하는 것으로
  간주합니다."
      그 함수의 헤더를 #include 하지 않았다(7절). 빌드는 되지만 결과가 틀릴 수 있다.
  error C1083 "포함 파일을 열 수 없습니다"
      헤더 이름이나 폴더가 틀렸다. "..."는 .c 파일과 같은 폴더에서 찾는다. Turboc.h처럼
      다른 폴더의 헤더는 -I가 필요하다(방법 1의 build.bat는 공부 폴더를 넣는다).
  E212 "쓸 파일을 열 수 없습니다" (gvim에서 저장할 때)
      폴더가 없다. :call mkdir('c\calc', 'p') 뒤 다시 저장한다(3절).


10. 디버깅 (F6)

- gvim과 Emacs의 F6은 현재 프로그램의 build\이름.exe를 Visual Studio 2022 디버거로 연다
  (devenv /DebugExe). main.c를 보고 있을 때 누르면 c\calc\build\main.exe가 열린다.
- 방법 1과 5.2의 빌드는 build\main.pdb(디버깅 정보)를 만든다. 5.3처럼 link를 따로 쓸 때는
  -debug를 빼먹지 않는다.
- Visual Studio에서 파일 > 열기 > 파일로 calc.c를 열고 줄 왼쪽을 눌러 중단점을 건 뒤 디버그
  > 디버깅 시작. F11로 main.c에서 Add 안(calc.c)으로 들어갈 수 있다.
- 소스를 고쳤으면 디버깅을 멈추고 gvim, Emacs에서 다시 빌드한다(Visual Studio는 빌드하지
  않는다). 디버깅 중에는 exe가 잠겨 빌드가 "is running"으로 멈춘다.
- 프로그램이 파일을 상대 경로로 열면 Visual Studio의 디버그 속성에서 작업 디렉터리를 소스
  폴더로 바꾼다(C_C++_빌드가이드.txt 10절).

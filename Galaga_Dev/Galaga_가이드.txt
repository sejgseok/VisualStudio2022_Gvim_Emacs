SPACE GALAGA: 초보자를 위한 구조 분석 및 코딩 학습 가이드
======================================================

분석 대상: Space_Galaga.sln과 연결된 실제 C 소스, 프로젝트 설정, 테스트
작성 기준: 2026-11-12 현재 작업 폴더의 코드

이 문서는 게임을 실행하는 방법뿐 아니라, 어떤 자료가 어디에 저장되고 어떤
함수들이 협력하여 게임을 움직이는지 설명한다. 먼저 원본을 실행해 본 뒤,
안내된 함수를 찾아 읽고 작은 부분부터 수정하면서 공부하는 것을 권장한다.
아래의 실습과 확장 아이디어는 학습 제안이며 현재 구현된 기능과 구분한다.

1. 게임 개요와 조작
===================

이 프로젝트는 순수 C17과 Windows API로 만든 세로형 슈팅 게임이다.
Unity 같은 게임 엔진이나 이미지 파일을 사용하지 않는다. 기체, 적, 탄환,
아이템, 글자는 Windows의 GDI 기능으로 직접 그린다. 사운드, 네트워크,
최고 점수 파일 저장 기능은 현재 없다.

플레이어는 화면 아래쪽에서 적 편대와 보스를 상대한다. 시작 목숨은 3개이며,
편대를 전멸시키면 다음 스테이지가 이어진다. 별도의 최종 승리 상태는 없다.

  Enter           타이틀에서 시작, 게임 오버 후 재시작
  방향키 / WASD   이동
  Space 유지      연속 사격
  Shift 유지      정밀 이동
  P               일시정지 / 계속하기
  F11             테두리 없는 전체 화면 / 원래 창으로 복귀
  R               게임 오버 후 재시작
  Esc             종료

창 전환이나 최소화 시 자동으로 일시정지한다. 돌아온 뒤 P로 재개한다.
P 키는 일시정지 입력이고, 화면에서 떨어지는 P 아이템은 무기 강화 아이템이다.


2. 솔루션과 프로젝트 설정 읽기
==============================

Space_Galaga.sln은 게임 로직을 담은 파일이 아니라 Visual Studio가 프로젝트와
빌드 구성을 묶어 관리하는 설정 파일이다. 이 솔루션에는 Space_Galaga라는
프로젝트 하나가 있고, Space_Galaga/Space_Galaga.vcxproj를 참조한다.

구성은 Debug/Release와 x64/x86의 조합이다. 솔루션의 x86은 프로젝트 내부의
Win32 플랫폼에 연결된다. 따라서 x86 출력 경로에는 Win32라는 이름이 쓰인다.

실제 컴파일 설정은 .vcxproj에서 확인한다.

  PlatformToolset=v143        Visual Studio 2022 컴파일 도구
  LanguageStandard_C=stdc17   C17 문법 사용
  CompileAs=CompileAsC        소스를 C로 컴파일
  /utf-8                     소스와 실행 문자 집합을 UTF-8로 처리
  UNICODE, _UNICODE          Windows 유니코드 API 사용 설정
  WarningLevel=Level4        높은 수준의 컴파일 경고
  TreatWarningAsError=true   경고도 오류로 취급
  SubSystem=Windows          게임 실행 시 콘솔 창을 만들지 않음
  user32.lib, gdi32.lib      창·입력 및 GDI 함수 연결

Debug는 최적화를 끄고 디버깅하기 쉽게 만든다. Release는 속도 최적화와
전체 프로그램 최적화를 사용한다. C 런타임은 Debug에서 /MTd, Release에서
/MT에 해당하는 정적 연결을 사용한다.

빌드 과정은 다음처럼 이해하면 된다.
  main.c와 game.c → 각각 컴파일 → .obj 파일
  .obj 파일 + Windows 라이브러리 → 링크 → Space_Galaga.exe
game.h는 두 소스에 포함되는 선언 파일이며, 혼자 실행 파일이 되지 않는다.

tests/game_tests.c는 현재 .vcxproj의 컴파일 목록에 없다. 게임 빌드와 별도로
18장의 명령으로 테스트 실행 파일을 만든다. .vcxproj.filters는 Visual Studio의
파일 표시 분류를 돕는 파일이며 게임 동작을 구현하지 않는다.


3. 개발 환경 준비와 빌드
========================

1) Visual Studio 2022의 'C++를 사용한 데스크톱 개발' 워크로드를 설치한다.
   C 컴파일러도 이 워크로드에 포함된다.
2) MSVC v143 및 Windows 10 또는 11 SDK를 준비한다.
3) Space_Galaga.sln을 연다.
4) 처음에는 Debug / x64를 선택한다.
5) Ctrl+Shift+B로 빌드하고 F5로 디버깅 실행한다.
   Ctrl+F5는 디버거 없이 실행한다.

명령행에서는 VS 2022 Developer PowerShell을 열고 저장소 루트로 이동한다.

  Set-Location C:\Users\User\Dev\Galaga_Dev
  msbuild .\Space_Galaga.sln /m /p:Configuration=Debug /p:Platform=x64
  .\bin\x64\Debug\Space_Galaga.exe

배포용 빌드는 Configuration=Release로 바꾼다.
생성 위치는 bin/<플랫폼>/<구성>/Space_Galaga.exe이다.
obj/에는 중간 산출물이, .vs/에는 Visual Studio 작업 정보가 들어간다.
이 폴더들의 생성 파일을 고쳐서 게임 기능을 변경하지 않는다.


4. 파일 구조와 책임 분리
========================

  Space_Galaga.sln                 솔루션 구성
  Space_Galaga/
    Space_Galaga.vcxproj           컴파일·링크·출력 경로 설정
    Space_Galaga.vcxproj.filters   IDE의 파일 분류
    main.c                        Windows 창과 프로그램 실행 환경
    game.h                        게임 자료 구조와 공개 함수 선언
    game.c                        게임 규칙과 GDI 렌더링
  tests/game_tests.c              창 없이 게임 규칙 검사
  README.md                      설치, 조작, 빌드 안내
  AGENTS.md                      저장소 기여 지침

main.c는 '창이 언제 입력을 받았는가, 언제 다시 그려야 하는가'를 처리한다.
game.c는 '입력에 따라 기체가 얼마나 움직이고 적에게 어떤 피해를 주는가'를
처리한다. 두 영역은 game.h의 다섯 함수로 연결된다.

  GameInit       처음 상태와 별 초기화
  GameKey        키 상태 저장 및 시작·일시정지 처리
  GameFocusLost  입력 해제 및 자동 일시정지
  GameUpdate     시간이 흐른 만큼 게임 상태 변경
  GameDraw       현재 상태를 화면에 그림

이 분리 덕분에 테스트는 창을 만들지 않고도 GameUpdate를 호출할 수 있다.
다만 game.h가 windows.h를 포함하고 game.c도 GDI에 의존하므로, 현재 구조가
운영체제와 완전히 독립적인 게임 엔진이라는 뜻은 아니다.


5. 이 코드에서 배우는 C 문법
============================

구조체: 관련 정보를 하나로 묶는다. Bullet은 탄환 하나의 위치와 속도를 묶고,
Game은 플레이 한 판을 진행하는 데 필요한 상태 전체를 묶는다.

포인터: Game *g는 Game 구조체의 주소를 전달받는다. g->score는 그 주소에
있는 구조체의 score 멤버를 뜻한다. 원본 상태를 변경할 수 있으며, 호출마다
커다란 Game 전체를 복사하지 않아도 된다. &g_game은 변수의 주소를 구한다.

const: GameDraw(const Game *g, ...)는 전달된 게임 자료를 이 포인터를 통해
수정하지 않겠다는 선언이다. 상태 갱신과 화면 표시를 구분하는 데 도움이 된다.

static: 파일 수준의 static 함수나 변수는 그 .c 파일 안에서만 직접 이름으로
참조할 수 있다. main.c의 g_game은 프로그램 실행 중 유지되는 실제 게임 상태다.
Shoot, Hit 같은 game.c 내부 함수는 game.h에 공개되지 않는다.

enum: MODE_TITLE 같은 상태에 의미 있는 이름을 붙인다. 숫자만 쓰는 것보다
조건문에서 의미를 읽기 쉽다.

#define: GAME_WIDTH, MAX_BULLETS 같은 상수 이름을 정의한다.
헤더의 #ifndef / #define / #endif는 중복 포함을 막는 헤더 가드다.

배열과 반복문: bullets[i]는 i번째 탄환이다. 인덱스는 0부터 시작하므로
MAX_BULLETS가 256이면 마지막 유효 인덱스는 255다.

memset: 메모리 영역을 같은 바이트 값으로 채운다. 이 코드에서는 구조체나
배열을 0으로 초기화하는 데 쓴다. sizeof(*g)는 Game 구조체 전체의 크기다.
GameInit처럼 필요한 필드를 다시 설정하는 과정까지 함께 읽어야 한다.

조건 연산자: 조건 ? 참일_때_값 : 거짓일_때_값 형태다.
예를 들어 enemy ? 5.0f : 4.0f는 적 탄환 반지름 5, 아군 탄환 반지름 4를 고른다.
실수 뒤의 f는 float 상수임을 뜻한다. 한글 문자열 앞 L은 넓은 문자 문자열이다.


6. 게임 자료 구조
==================

game.h의 핵심은 다음과 같다.

  GameMode: TITLE, PLAY, PAUSE, OVER 네 가지 상태
  Bullet: active, enemy, x/y, vx/vy, radius
  Enemy: active, type, hp/maxHp, diving, 위치, 편대 기준점, 타이머
  Particle: active, 위치, 속도, life/maxLife, 색
  Star: 위치, 아래로 흐르는 속도, 크기
  Item: active와 위치

Game에는 다음 정보가 들어 있다.
  mode                         현재 게임 상태
  keys[256]                    가상 키 코드별 눌림 여부
  randomState                  이 게임이 사용하는 난수 상태
  score, bestScore             이번 점수와 실행 중 최고 점수
  lives, stage                 남은 목숨과 현재 스테이지
  enemyCount, kills            살아 있는 적 수와 누적 격파 수
  playerX, playerY             플레이어 중심 좌표
  shotTime                     다음 발사까지 기다리는 시간
  invincibleTime, powerTime    무적과 강화의 남은 시간
  time, waveDelay, flashTime   플레이 시간, 편대 전환 대기, 피격 효과 시간

배열 최대 용량은 적 48, 탄환 256, 입자 320, 별 100, 아이템 12다.
일반 편대는 적 40기를 사용하므로 적 배열에는 여유가 있다.

탄환·적·입자·아이템은 active가 0이면 비활성 슬롯이고 1이면 사용 중이다.
새 탄환을 만들 때 malloc으로 할당하지 않고 빈 슬롯을 찾아 재사용한다.
이 방식을 간단한 객체 풀이라고 부를 수 있다. 메모리 사용량은 예측하기 쉽지만,
배열이 가득 차면 Shoot은 발사를 생략한다. 플레이어와 적이 탄환 배열을 공유하므로
슬롯 부족은 양쪽 사격에 영향을 줄 수 있다.

학습 질문: 탄환을 지울 때 배열 요소를 앞으로 당길 필요가 있을까?
이 코드는 active만 0으로 바꾸고 다음 생성 시 재사용하므로 그럴 필요가 없다.


7. 프로그램 실행 흐름과 Windows 메시지
=======================================

main.c의 진입점은 콘솔 프로그램의 main이 아니라 wWinMain이다.

  wWinMain
    → DPI 설정 및 창 클래스 등록
    → CreateWindowExW로 창 생성
        → WindowProc에서 WM_CREATE 처리
            → 백 버퍼 생성, GameInit, 타이머 등록
    → ShowWindow, UpdateWindow
    → GetMessageW 반복
        → TranslateMessage
        → DispatchMessageW
            → WindowProc에서 각 메시지 처리
    → 종료 메시지 수신 후 GDI 자원 정리

창 클래스는 어떤 콜백 함수를 사용해 메시지를 처리할지 등록하는 Windows의
설정 단위다. 여기서 클래스라는 말은 C++ class 문법을 뜻하지 않는다.

WindowProc는 Windows가 호출하는 메시지 처리 함수다.

  WM_CREATE      800×900 백 버퍼 생성, 초기화, 8ms 타이머 요청
  WM_TIMER       Tick 호출
  WM_KEYDOWN     Esc/F11 처리 또는 GameKey로 누름 전달
  WM_KEYUP       GameKey로 뗌 전달
  WM_KILLFOCUS   GameFocusLost 호출
  WM_SIZE        최소화되었으면 GameFocusLost 호출
  WM_ERASEBKGND  기본 배경 지우기를 생략하여 깜빡임 억제
  WM_PAINT       BeginPaint → PaintGame → EndPaint
  WM_DESTROY     타이머 해제, PostQuitMessage로 루프 종료 요청

GetMessageW는 메시지가 있으면 양수, 종료 메시지면 0, 오류면 -1을 반환한다.
코드는 -1도 구분한다. 처리하지 않는 메시지는 DefWindowProcW에 맡긴다.

중요: 입력 메시지를 받았다고 곧바로 이동량을 더하지 않는다. 입력은 저장하고,
실제 이동은 고정된 시간 간격의 GameUpdate에서 계산한다.


8. 게임 상태와 초기화
======================

상태 전이는 다음과 같다.

  MODE_TITLE --Enter--> MODE_PLAY
  MODE_PLAY  --P 또는 포커스 상실--> MODE_PAUSE
  MODE_PAUSE --P--> MODE_PLAY
  MODE_PLAY  --목숨 소진--> MODE_OVER
  MODE_OVER  --Enter 또는 R--> MODE_PLAY

GameInit은 프로그램 시작 시 구조체 전체를 지우고 타이틀 상태로 설정한다.
GetTickCount를 이용해 난수 상태를 잡고 별 100개의 위치·속도·크기를 정한다.

StartGame은 새 판을 시작한다. 탄환·입자·아이템·키를 비우고 점수 0, 목숨 3,
stage 0, 누적 격파 0으로 설정한다. 플레이어 시작점은 (400, 770), 시작 무적은
2초다. MODE_PLAY로 바꾼 뒤 SpawnWave를 호출하여 stage가 1이 된다.

재시작에서는 bestScore, 별 배열, 난수 상태를 보존한다. GameInit과 StartGame의
차이를 이해하면 '프로그램 최초 초기화'와 '새 게임 초기화'를 구분할 수 있다.
최고 점수는 메모리에만 있으므로 프로그램을 종료하면 사라진다.

일시정지는 GameUpdate 첫 부분에서 즉시 반환하므로 별과 입자도 멈춘다.
타이틀과 게임 오버에서는 별·입자만 갱신되고 실제 전투는 진행하지 않는다.
GameDraw는 계속 호출될 수 있어 창이 가려졌다 드러나도 정지 화면을 다시 그린다.


9. 시간 처리와 게임 루프
========================

화면 좌표는 왼쪽 위가 (0, 0), 오른쪽이 +x, 아래쪽이 +y다.
논리 화면은 800×900이며 모든 게임 시간은 초 단위다.

이동의 기본 공식은 '새 위치 = 이전 위치 + 초당 속도 × 경과 시간'이다.
예를 들어 오른쪽으로 초당 390픽셀 이동하면 1/120초 동안 이동량은 3.25다.
float로 위치를 저장해야 이런 소수점 이동을 잃지 않는다.

Tick은 QueryPerformanceCounter와 QueryPerformanceFrequency를 이용해 실제
경과 시간을 구한다. 타이머는 8ms를 요청하지만 정확한 주기로 보장되지 않는다.
따라서 타이머가 왔다고 항상 같은 시간을 가정하지 않고 누적 시간을 사용한다.

실제 알고리즘을 줄이면 다음과 같다.

  elapsed = 실제 경과 시간;
  elapsed가 0.1초보다 크면 0.1초로 제한;
  accumulator += elapsed;
  while (accumulator >= 1.0 / 120.0) {
      GameUpdate(..., 1.0f / 120.0f);
      accumulator -= 1.0 / 120.0;
  }
  InvalidateRect(...);  /* 다시 그려야 한다고 알림 */

0.02초가 쌓였다면 업데이트를 두 번 수행하고 약 0.00333초를 남긴다.
남은 시간을 버리지 않으므로 작은 시간 오차가 계속 누적되는 것을 줄인다.
긴 지연을 0.1초로 제한하는 것은 디버거 중단 후 갑자기 멀리 이동하거나
업데이트를 지나치게 많이 실행하는 상황을 줄이기 위한 선택이다.
대신 긴 정지 시간 전체를 게임 시간으로 따라잡지는 않는다.

업데이트 빈도 120Hz와 실제 화면 표시 FPS는 같은 개념이 아니다.
WM_PAINT 일정과 시스템 부하에 따라 그리는 횟수는 달라진다. 현재 코드는
렌더링 보간이나 수직 동기화를 별도로 구현하지 않는다.


10. 입력과 플레이어 이동
=========================

GameKey는 키 코드가 256 미만이면 keys[key]에 누름 여부를 기록한다.
이동과 사격은 이 배열을 매 업데이트마다 읽는다.

반면 시작·일시정지 같은 기능은 키를 처음 누른 순간에만 처리한다.
WM_KEYDOWN의 lParam 30번 비트로 자동 반복인지 검사하여 GameKey에 전달한다.
GameKey는 repeat가 참이면 상태 전환을 생략한다. P를 오래 눌러도 정지와
재개가 빠르게 반복되지 않는 이유다.

이동 방향 계산은 다음 원리다.

  dx = 오른쪽_눌림 - 왼쪽_눌림;
  dy = 아래쪽_눌림 - 위쪽_눌림;

오른쪽만 누르면 dx=1, 왼쪽만 누르면 -1, 둘 다 누르면 0이다.
대각선 (1, 1)의 길이는 sqrt(2)이므로 그대로 쓰면 직선보다 빨라진다.
코드는 sqrtf(dx*dx + dy*dy)로 길이를 구한 뒤 방향을 길이로 나눈다.
이 과정을 정규화라고 하며 방향은 유지하고 길이는 1로 만든다.
길이가 0일 때는 나누지 않아 0으로 나누는 오류를 피한다.

기본 속도는 390, Shift 속도는 190픽셀/초다.
현재 실제 이동 제한은 x=36~764, y=460~780이다.
Clamp는 값이 범위를 벗어나면 가장 가까운 경계값으로 제한한다.
상단 적 영역과 하단 안내 패널을 침범하지 않도록 이동 범위를 정한 것이다.

GameFocusLost는 모든 키를 해제한다. Alt+Tab 도중 키를 놓으면 게임 창이
WM_KEYUP을 받지 못해 계속 이동할 수 있기 때문이다.


11. 탄환 생성과 연속 사격
=========================

Shoot은 비활성 Bullet을 하나 찾아 위치·속도·소속·반지름을 설정한다.
enemy=0은 플레이어 탄환, 1은 적 탄환이다.

기본 발사:
  위치 (playerX, playerY-22), 속도 (0, -680)
  간격 0.17초, 대략 초당 5.9회

강화 발사:
  기본 중앙 탄환에 왼쪽 (-140, -650), 오른쪽 (140, -650) 탄환 추가
  간격 0.12초, 대략 초당 8.3회

위쪽으로 가므로 vy가 음수다. 양옆 탄환의 vx가 각각 음수·양수이므로
시간이 지날수록 좌우로 퍼진다.

GameUpdate는 shotTime에서 dt를 빼고, Space가 눌렸으며 shotTime<=0이면
발사한 뒤 대기 시간을 다시 설정한다. OS의 키 반복 속도에 의존하지 않는다.

매 업데이트마다 탄환 위치에 vx*dt, vy*dt를 더한다. 화면 바깥 20픽셀을
넘어간 탄환은 active=0으로 되돌린다. 배열 용량이 부족한 강화 사격은 세 발이
모두 생성되지 않을 수도 있다. Shoot은 슬롯 부족을 반환값으로 알리지는 않는다.


12. 적 편대, 급강하, 조준 공격
==============================

SpawnWave는 적과 탄환 배열을 비우고 stage를 증가시킨다.
일반 스테이지는 5행×8열, 총 40기다. 인덱스는 row*8+column으로 계산한다.

  row=0       장갑형 type 2, 체력 2, 8기
  row=1~2     중급형 type 1, 체력 1, 16기
  row=3~4     일반형 type 0, 체력 1, 16기

기준 위치는 homeX=120+column*80, homeY=165+row*58이다.
처음 y는 -100-row*55로 화면 위쪽에 배치한다.

UpdateEnemies에서는 일반 편대의 x를 sinf(g->time*1.2f)*42만큼 흔든다.
y는 목표 위치와 현재 위치 차이의 일부를 더하여 부드럽게 진입시킨다.

  y += (목표y - y) * Clamp(dt*3, 0, 1);

이 식은 일정 속도 이동과 다르다. 목표까지 거리가 멀면 빨리, 가까우면
천천히 다가간다. sinf는 반복적인 움직임을 만드는 사인 함수이며 입력은
라디안이다. 곱하는 값은 진폭이나 변화 속도를 조절한다.

플레이 시간이 2.5초를 넘으면 일반 적은 매 업데이트마다 다음 조건으로
급강하를 시작할 수 있다.
  Random01(g) < dt * (0.013f + difficulty*0.003f)
dt를 곱하므로 업데이트 한 번이 아니라 시간에 비례한 빈도로 발생하도록 한다.

급강하 중에는 y가 초당 170+difficulty*9만큼 증가하고 x도 사인 곡선 형태로
변한다. 아래로 화면을 벗어나면 diving=0, y=-45로 바뀌고 편대로 다시 진입한다.
모든 적이 하나의 복잡한 AI를 갖는 대신 조건에 따라 이동 공식을 바꾸는 구조다.

fireTime이 끝나고 적이 y>60, y<playerY-50 조건을 만족하면 조준탄을 쏜다.
플레이어까지의 (dx,dy)를 길이로 나눈 뒤 탄속을 곱해 속도를 얻는다.
발사 이후에는 방향을 다시 계산하지 않으므로 유도탄이 아니라 직선 조준탄이다.
일반 적의 다음 사격 대기는 3+Random01(g)*6-difficulty*0.09초다.


13. 보스와 난이도
==================

stage%5==0이면 일반 편대 대신 보스 한 기를 생성한다.
보스 체력은 65+stage*3이므로 5스테이지 보스는 80, 10스테이지 보스는 95다.

보스의 위치는 다음과 같다.
  x = 400 + sinf(time*0.8f)*245
  y = 185 + sinf(time*1.6f)*38
서로 다른 주기로 좌우·상하를 반복하며, 그림 위에 hp/maxHp 비율의 체력 막대를
표시한다. 이 time은 해당 Enemy의 누적 시간이다.

사격할 때는 플레이어 조준탄 한 발에 더해 k=-2~2의 다섯 탄환을 발사한다.
추가 탄환 vx는 k*85, vy는 235+difficulty*5다. 따라서 최대 여섯 발이 나오며
다섯 발은 방향 각도가 같은 간격인 부채꼴이 아니라 수평 속도가 다른 패턴이다.

공격·이동에 사용하는 difficulty는 stage를 1~16으로 제한한 값이다.
적 조준탄 속도는 190+difficulty*9이므로 최대 334픽셀/초다.
보스 사격 간격 식은 Clamp(1.2-difficulty*0.03, 0.55, 1.2)이며 현재 난이도
상한 16에서는 0.72초까지 줄어든다. 0.55초는 보호용 하한이지만 현재 식의
상한 조합에서는 도달하지 않는다.

주의: difficulty에 상한이 있어도 보스 체력 계산의 stage에는 상한이 없다.
따라서 모든 난이도 요소가 16스테이지 이후 동일해지는 것은 아니다.


14. 충돌, 피해, 점수, 아이템
============================

Hit 함수는 두 점 사이 거리의 제곱을 검사한다.

  dx = ax-bx;
  dy = ay-by;
  return dx*dx + dy*dy < radius*radius;

매번 제곱근을 구하지 않아도 원 내부 여부를 알 수 있다. 경계와 정확히 같으면
참이 아닌 엄격한 '<' 비교다. radius 인자는 각 호출에서 정한 유효 판정 거리이며,
항상 두 객체의 반지름을 자동으로 더해 주는 함수는 아니다.

현재 판정 거리:
  적 탄환 → 플레이어       10 + b->radius = 15
  아군 탄환 → 일반 적     23
  아군 탄환 → 보스        54
  적 몸체 → 플레이어      일반 27, 보스 65
  아이템 → 플레이어       32

플레이어 탄환은 적 하나에 맞으면 비활성화하고 적 체력을 1 줄인다.
체력이 0 이하가 되면 DestroyEnemy를 호출한다. 내부 적 탐색의 break 때문에
한 발이 여러 적을 동시에 관통하지 않는다.

DamagePlayer는 무적이거나 플레이 상태가 아니면 아무것도 하지 않는다.
피격 시 목숨 1 감소, 강화 해제, 무적 2.5초, 테두리 효과 0.18초를 적용하고
현재 적 탄환을 모두 제거한다. 플레이어 위치를 시작점으로 옮기지는 않는다.
목숨이 0이면 MODE_OVER로 바꾼다. 무적 중 기체 깜빡임은 그리기 조건으로 구현한다.

DestroyEnemy는 active=0, enemyCount 감소, kills 증가를 함께 처리한다.
일반형·중급형·장갑형은 각각 100·200·300점이고, 급강하 중이면 150·300·450점이다.
보스는 3,000점이다. enemyCount와 실제 active 적 수는 항상 일치해야 한다.

누적 kills가 7의 배수이거나 보스를 격파하면 빈 아이템 슬롯에 P를 만든다.
두 조건이 동시에 참이어도 이 코드에서는 한 개만 생성한다. 슬롯이 가득 차면
아이템은 생성되지 않는다. kills는 스테이지가 바뀌어도 누적된다.

아이템은 초당 115픽셀로 아래로 떨어진다. 획득하면 50점을 더하고 powerTime을
12초로 설정한다. 기존 시간에 12초를 더하는 방식은 아니다.
적 격파와 아이템 획득 모두 bestScore를 갱신한다.

enemyCount가 0이면 waveDelay가 증가하고 2.5초를 초과할 때 다음 편대를 만든다.
대기 중에도 이동·사격·아이템 획득이 가능하며 남아 있는 적 탄환도 움직인다.
다음 편대 생성 시 적·탄환은 초기화하지만 아이템과 입자까지 지우지는 않는다.


15. 배경 별과 폭발 입자
=======================

별은 서로 다른 속도로 아래로 움직인다. 아래를 벗어나면 y=0으로 돌리고
x를 다시 무작위로 정한다. 속도에 따라 밝기와 크기도 달라 깊이감을 만든다.

Burst는 빈 입자에 무작위 각도·속도·수명을 설정한다.
  vx = cosf(angle)*speed
  vy = sinf(angle)*speed
원 둘레의 방향을 이용해 사방으로 퍼지는 폭발을 만드는 것이다.
입자는 life가 0 이하가 되면 비활성화한다. life/maxLife를 원래 RGB 색에
곱하여 점차 어두워지게 한다. 별도의 반투명 이미지 합성은 사용하지 않는다.

Random01은 randomState를 갱신하는 선형 합동 방식의 간단한 의사 난수다.
반환 범위는 실제로 0 이상 1 미만이다. 같은 시작 상태와 같은 호출 순서라면
같은 수열을 얻어 테스트 재현에 도움이 된다. 보안용 난수로 쓰는 기능은 아니다.


16. GDI 그리기와 화면 크기
==========================

HDC는 그리기 대상과 현재 그리기 설정을 담는 장치 컨텍스트 핸들이다.
화면 DC에 도형을 하나씩 바로 그리면 그려지는 중간 상태가 보일 수 있다.
이 게임은 메모리에 완성한 그림을 창으로 복사하는 더블 버퍼링을 사용한다.

  WM_CREATE: 호환 DC와 800×900 비트맵 생성
  GameDraw: 메모리 DC에 한 화면 전체 그리기
  PaintGame: StretchBlt로 창 크기에 맞춰 복사
  종료: 원래 비트맵 선택 복구 → 비트맵 삭제 → 메모리 DC 삭제

GameDraw의 그리기 순서는 배경 → 별 → 적 → 탄환 → 아이템 → 플레이어 →
입자 → 상단 HUD·하단 안내 → 상태별 패널·문구 → 피격 테두리다.
나중에 그린 것이 앞 내용을 덮는다. HUD를 나중에 그려 점수 표시를 보호한다.

도형 보조 함수:
  Box     FillRect로 사각형
  Oval    Ellipse로 타원
  Shape   Polygon으로 다각형
  Label   DrawTextW로 한글·영문 텍스트
  DrawShip, DrawEnemy   위 도형들을 조합한 기체와 적

한글은 L"문자열"과 W 접미사의 Windows API로 처리한다. 글꼴은 맑은 고딕이며
GameDraw에서 27/38/86 높이의 글꼴을 만들어 프레임 내에서 재사용한 뒤 삭제한다.
소스 UTF-8 설정과 Windows의 넓은 문자 문자열은 서로 다른 층의 개념이다.

DrawShip과 DrawEnemy는 SaveDC/RestoreDC 및 XFORM으로 도형을 중심점 기준
1.5배 확대한다. x'=1.5*x-0.5*중심x와 같은 변환으로 중심이 움직이지 않는다.
이 변환은 그리기에만 적용된다. 논리 위치나 충돌 거리도 1.5배가 되는 것은 아니다.

논리 화면은 항상 800×900이다. PaintGame은 가로세로 비율을 유지하는 최대
표시 크기를 계산하고 남는 바깥 영역을 검정색으로 채운다. HALFTONE 방식으로
축소·확대 복사한다. 창 크기가 바뀌어도 게임 속도와 충돌 좌표는 바뀌지 않는다.

시작 창은 클라이언트 영역 1200×1350을 요청하며, 모니터 작업 영역보다 크면
최대화한다. F11은 현재 모니터 크기의 테두리 없는 창으로 전환하며 원래 위치를
WINDOWPLACEMENT에 보관했다가 복구한다. 모니터 해상도를 바꾸는 방식은 아니다.

GDI 자원 관리의 원칙은 '만들기 → 선택 → 사용 → 원래 선택 복구 → 삭제'다.
CreateSolidBrush/CreateFontW 등으로 만든 자원은 해제해야 한다. GetStockObject로
얻은 운영체제 제공 객체는 직접 삭제하지 않는다. 매 프레임 생성하는 자원을
누락하면 오래 실행할 때 그리기 오류가 생길 수 있다.


17. 함수 찾아보기와 한 프레임 추적
==================================

기능을 수정하려면 다음 위치부터 찾아본다.
  창 크기·종료·전체 화면             main.c: wWinMain, WindowProc, ToggleFullscreen
  업데이트 주기                     main.c: Tick
  화면 비율·백 버퍼 복사             main.c: PaintGame
  용량·상태·공개 함수                game.h
  새 게임 초기값                    game.c: StartGame
  편대·보스 생성                    game.c: SpawnWave
  이동·사격·탄환·아이템·스테이지      game.c: GameUpdate
  적 움직임·공격                    game.c: UpdateEnemies
  피해·점수·아이템 생성              game.c: DamagePlayer, DestroyEnemy
  그림·한글 UI                      game.c: GameDraw 및 Draw* 보조 함수

플레이 중 GameUpdate 한 번의 순서는 다음과 같다.
  1) 일시정지면 반환
  2) 별과 기존 입자 갱신
  3) PLAY가 아니면 반환
  4) 게임 시간 및 무적·강화·피격 효과 시간 갱신
  5) 플레이어 이동, 발사 대기 및 발사 처리
  6) 적 이동·발사·몸체 충돌 처리
  7) 게임 오버가 되었으면 반환
  8) 탄환 이동·화면 이탈·충돌 처리
  9) 아이템 이동·획득 처리
 10) 편대 전멸 시 다음 스테이지 대기 처리

예를 들어 아군 탄환이 장갑형 적에게 맞으면 다음 연결이 생긴다.
  GameUpdate → Hit 성공 → 탄환 비활성화 → hp 1 감소 → Burst
  → hp가 0 이하면 DestroyEnemy → 점수·격파 수 변경 → 아이템 조건 검사
  → 남은 적이 없으면 waveDelay 증가
  → 이후 WM_PAINT에서 변경된 상태가 그림으로 나타남

이처럼 '상태를 바꾸는 함수'와 '그 상태를 표시하는 함수'를 연결해 읽는다.
그림만 숨긴다고 실제 적이 사라지는 것은 아니며 active, enemyCount 같은
게임 상태도 함께 일관되게 변경해야 한다.


18. 테스트와 디버깅
===================

테스트는 tests/game_tests.c의 main에서 표준 C assert로 조건을 확인한다.
다음 명령은 x64 개발 환경의 VS 2022 Developer PowerShell에서 루트 기준으로
실행한다. cl 명령은 줄 전체를 한 명령으로 입력한다.

  New-Item -ItemType Directory -Force obj/tests, bin/tests
  cl /nologo /TC /std:c17 /utf-8 /W4 /WX /MTd /Od /RTC1 /Foobj/tests/ /Febin/tests/game_tests.exe tests/game_tests.c Space_Galaga/game.c /link /SUBSYSTEM:CONSOLE user32.lib gdi32.lib
  .\bin\tests\game_tests.exe

주요 옵션은 /TC=C 컴파일, /std:c17=C17, /utf-8=인코딩, /W4 /WX=경고 엄격
처리, /Od=최적화 끔, /RTC1=런타임 검사, /SUBSYSTEM:CONSOLE=콘솔 테스트다.
assert가 제거되지 않도록 이 테스트에서 NDEBUG를 정의하지 않는다.

Reset은 GameInit 후 randomState=12345로 설정하고 Enter 입력을 전달한다.
이는 이후 게임 난수 흐름을 재현하기 위한 것이며 이미 GameInit에서 생성된
별의 초기 배치까지 고정하는 것은 아니다.

검사 항목은 다음과 같다.
  - 대각선 이동 거리와 속도 정규화
  - 포커스 상실 시 키 해제 및 일시정지
  - P 자동 반복으로 상태가 다시 바뀌지 않는지
  - 아이템 획득, 12초 강화와 세 발 생성
  - 피격, 무적, 목숨 소진, 재시작 시 최고 점수 보존
  - 장갑형 적 두 발 격파, 점수 및 남은 적 수
  - 다음 스테이지 전환과 5스테이지 보스 생성
  - 72,000회×1/120초, 즉 10분 분량의 가상 업데이트

장기 검사는 무적을 유지하고 일정 간격으로 편대를 강제 제거한다. 실제로
10분을 기다리는 테스트가 아니며 자연 플레이 난이도나 화면 품질을 검증하는
것도 아니다. 유한한 좌표, 적 수 일관성, 여러 스테이지 진행 등을 확인한다.
현재 x 경계 검사는 24~GAME_WIDTH-24로 실제 이동 제한 36~764보다 느슨하다.
경계 이동을 수정하는 실습에서는 정확한 경계 테스트를 보완하면 좋다.

F9로 중단점을 설정하고 F10으로 한 줄씩 실행한다. 처음 볼 위치는
StartGame, GameUpdate의 발사 분기, DamagePlayer, DestroyEnemy다.
조사식에는 g->mode, g->lives, g->enemyCount, g->powerTime 등을 추가한다.
GameUpdate는 자주 호출되므로 무조건 멈추기보다 조건부 중단점을 활용한다.
예를 들어 '특정 적의 hp가 1일 때' 또는 'g->lives == 1일 때'를 관찰한다.

논리 테스트와 별도로 창 크기 변경, F11 왕복, 최소화, Alt+Tab, 한글 잘림은
게임을 실행해 눈으로 확인해야 한다. 이 문서 작성에서는 실행 테스트를 새로
수행하지 않았으며, 위 설명은 소스 및 설정 분석을 기준으로 한다.


19. 단계별 코딩 실습
====================

매 실습마다 원본을 보관하고 '한 가지 수정 → 빌드 → 동작 확인' 순서를 따른다.
아래 수치는 실습 예시이며 원본 게임에는 적용하지 않았다.

실습 1: 플레이어 속도 조절
  위치: GameUpdate의 speed 선택식
  변경: 기본 390을 300으로 바꾼다.
  관찰: 상하좌우와 대각선의 이동 속도가 동일하게 느려지는지 확인한다.
  검사: 기존 이동 테스트는 390을 기대하므로 설계 변경에 맞춰 기대값도 바꾼다.
  배우는 것: 속도, dt, 정규화, 테스트 기대값의 관계.

실습 2: 시작 목숨 변경
  위치: StartGame의 lives=3
  변경: 5로 바꾸고 HUD와 게임 오버 시점을 확인한다.
  검사: Reset의 초기 목숨 검사와 3회 피격 루프도 새 규칙에 맞게 조정한다.
  배우는 것: 초기화 값 하나가 여러 테스트와 게임 규칙에 연결되는 방식.

실습 3: 발사 간격 조절
  위치: GameUpdate의 shotTime 재설정
  변경: 기본 0.17f를 0.25f로 바꾼다.
  관찰: 1초 동안 대략 네 번 발사되는지, 강화 사격 간격은 유지되는지 확인한다.
  주의: dt를 바꾸거나 키 반복 처리를 수정할 필요는 없다.
  배우는 것: 쿨다운 방식의 시간 제어.

실습 4: 강화 시간과 안내 문구 함께 수정
  위치: 아이템 획득의 powerTime=12와 GameDraw의 타이틀 설명
  변경: 8초로 바꾼다. 테스트의 12초 기대값과 README 설명도 맞춘다.
  개선: 공통 상수를 정의해 규칙 값의 중복을 줄이는 방법을 생각해 본다.
  배우는 것: 게임 규칙, UI, 테스트, 문서의 일치.

실습 5: 적 색상 바꾸기
  위치: DrawEnemy의 COLORREF 선택
  변경: type 0의 RGB 색을 바꾼다.
  관찰: 체력이나 충돌은 바뀌지 않고 외형만 변하는지 확인한다.
  배우는 것: 렌더링 데이터와 전투 데이터의 구분.

실습 6: 점수 규칙 변경
  위치: DestroyEnemy의 점수 계산식
  변경: 일반 적 기본 점수를 늘린다.
  검사: 적 격파 테스트의 score 및 bestScore 기대값을 함께 수정한다.
  배우는 것: 삼항 연산자, 누적 점수, 회귀 테스트.

실습 7: 작은 테스트 추가
  위치: tests/game_tests.c
  절차: Reset 후 키를 누르고 GameUpdate를 여러 번 호출한 뒤 경계를 검사한다.
  예시: 왼쪽으로 충분히 이동시킨 후 assert(game.playerX == 36.0f).
  별도 Reset 후 Shift+오른쪽으로 한 번 갱신하여 이동량이 190*step인지 검사한다.
  실수 계산 결과 비교에는 fabsf(실제값-기대값)<허용오차를 사용한다.
  배우는 것: 조건 준비 → 동작 실행 → 결과 검증의 테스트 구성.

실습 8: 보스 연습 모드 만들기
  위치: StartGame과 SpawnWave의 연결
  임시 변경: 시작 stage를 4로 두면 SpawnWave의 증가 후 5가 되어 보스가 나온다.
  관찰: 체력 80, 이동, 조준탄과 추가 다섯 탄환을 확인한다.
  주의: 최초 stage=1을 기대하는 기존 테스트는 이 임시 변경과 맞지 않는다.
  연습 후 원복하거나 테스트 전용 상태 구성으로 분리한다.

원본부터 직접 재작성하고 싶다면 다음 순서로 작은 동작 단위를 완성한다.
  빈 Win32 창 → 단색 배경 → 플레이어 도형 → 키 입력 이동 → dt 기반 이동
  → 단일 탄환 → 고정 배열 재사용 → 적 한 기 → 충돌과 체력
  → 편대 생성 → 점수·아이템 → 상태 전환 → 보스 → UI·테스트
완성 코드 전체를 한 번에 복사하기보다 각 단계가 동작한 이유를 설명해 본다.


20. 자주 생기는 문제와 확장 과제
================================

[빌드 명령을 찾을 수 없음]
일반 PowerShell 대신 VS Developer PowerShell에서 실행한다. MSVC v143과
Windows SDK가 설치되었는지도 확인한다.

[수정했는데 예전 게임이 실행됨]
선택한 Debug/Release 및 x64/Win32 출력 경로를 확인한다. 실행 중인 게임을
종료한 다음 다시 빌드한다. 다른 구성 폴더의 exe를 실행하지 않았는지 확인한다.

[한글이 깨짐]
소스를 UTF-8로 저장하고 /utf-8 설정을 유지한다. UI 문자열은 기존 L"..."와
W 계열 API 사용 방식을 따른다. 문자열 변경 후 실제 창에서도 확인한다.

[대각선이 빠르거나 키를 놓아도 계속 이동함]
정규화 코드, WM_KEYUP 전달, GameFocusLost의 키 초기화를 차례로 확인한다.

[적을 없앴는데 다음 스테이지가 시작되지 않음]
active만 바꾸고 enemyCount를 줄이지 않았는지 확인한다. 정상 격파는
DestroyEnemy를 통해 처리한다. 테스트가 두 값을 함께 확인하는 이유다.

[그림과 충돌이 맞지 않음]
현재 게임은 의도적으로 외형보다 작은 충돌 영역을 사용한다. 확대 변환은
그림에만 적용된다. 도형 좌표와 Hit 호출의 거리 값을 따로 살펴본다.

[오래 실행하면 그리기가 이상해짐]
추가한 브러시·글꼴·비트맵의 해제와 선택 복구를 확인한다. 최적화 과제로
매 프레임 생성하는 글꼴을 미리 만들고 종료 시 해제하는 방법을 검토할 수 있다.
이 경우 초기화 실패 처리와 종료 경로도 함께 설계해야 한다.

다음 기능은 현재 없으며, 기본 구조를 익힌 뒤 도전할 확장 과제다.
  - 최고 점수 저장: 파일 읽기·쓰기, 파일 부재·잘못된 내용 처리
  - 사운드: 발사·피격 이벤트와 재생 기능 연결
  - 설정 상수 정리: 속도·강화 시간·점수 등의 중복값 감소
  - 적 유형 추가: type별 체력·이동·공격·점수·그림·테스트 함께 설계
  - 일시정지 메뉴: 메뉴 상태와 입력 전환 규칙 정의
  - 로직과 렌더링 분리: game.c의 GDI 의존성을 별도 파일로 이동
  - 고속 탄환 충돌 개선: 한 번의 이동 구간 전체를 검사해 통과 현상 줄이기

학습을 마친 뒤에는 다음 질문에 자기 말로 답해 본다.
  1) 왜 키 메시지에서 직접 위치를 바꾸지 않는가?
  2) dt를 곱하지 않으면 다른 PC에서 어떤 차이가 생기는가?
  3) active와 enemyCount가 서로 다르면 어떤 오류가 생기는가?
  4) GameInit과 StartGame은 왜 따로 필요한가?
  5) 창 크기가 달라도 충돌 좌표를 바꾸지 않아도 되는 이유는 무엇인가?
  6) 테스트가 통과해도 실제 창에서 확인해야 할 것은 무엇인가?

이 질문을 소스의 함수와 연결해서 설명할 수 있다면, 이 프로젝트의 핵심인
상태 관리, 입력, 시간 기반 이동, 충돌, 렌더링, 검증의 연결을 이해한 것이다.
